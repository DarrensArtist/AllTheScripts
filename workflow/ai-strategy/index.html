Workflow · AI Strategy

Use AI to expose and execute decisions—not to silently make them.

AI can accelerate analysis, documentation and bounded implementation. The developer retains product intent, architectural approval and responsibility for the result.

Responsibility model

AI supports

Analysis and bounded execution

  • Find omissions, contradictions and dependency risks.
  • Draft structured artefacts from approved inputs.
  • Implement clearly scoped tasks.
  • Run checks and summarise evidence.
  • Maintain handoff and audit records.
Developer owns

Intent, approval and accountability

  • Choose the player experience and project boundary.
  • Approve architecture and trade-offs.
  • Resolve material ambiguity.
  • Judge whether evidence is sufficient.
  • Accept, reject or defer revisions.

Missing-detail lenses

Before execution, inspect the work through several lenses. A plausible answer is not the same as an approved decision.

Experience

Player action, feedback, clarity, pacing and failure.

System

State, rules, contracts, lifecycle and error behaviour.

Production

Scope, dependencies, ordering, assets and tools.

Verification

Acceptance evidence, test environment and limitations.

Context strategy

Use the smallest complete context package for the current decision. Too little context invites invention; too much hides the active boundary.

  1. State the current phase and exact objective.
  2. Provide approved source documents, not reconstructed summaries.
  3. Name files, modules and behaviours that are in and out of scope.
  4. List unresolved questions and forbid assumption where they are material.
  5. Define the output format, verification and stop condition.

Operating model

1 · Framing

Give the objective, user impact, constraints and definition of useful completion.

2 · Questioning

Ask AI to identify missing information by lens. The developer answers or explicitly defers each material point.

3 · Documentation

Create artefacts in workflow order and keep one source of truth for each decision.

4 · Handoff

Record phase, module, activity, status, completed evidence, blockers and next valid action.

5 · Review

Compare output with approved intent, affected contracts and acceptance checks—not only with the last instruction.

6 · Recovery

When work drifts, stop. Identify the last trusted state, preserve evidence and choose repair, revert or re-plan.

7 · Branching

Explore alternatives separately when they could materially change scope or architecture. Merge only an explicitly chosen result.

8 · Implementation

Give AI one bounded task or a proven-safe independent batch. Preserve unrelated work and verify each claim.

9 · Verification

Require commands, observations or artefacts that another person can inspect. State anything that was not tested.

10 · Audit

Check that code, tests, documentation and resume state describe the same project before declaring the slice complete.

Stop conditions

Pause AI execution when:

  • a material product or architectural choice is missing;
  • the requested change exceeds the approved slice;
  • source documents disagree;
  • verification cannot demonstrate the claim;
  • the next action would overwrite unrelated work.
