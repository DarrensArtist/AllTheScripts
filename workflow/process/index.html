Workflow · Process

Move forward only when the next step is supported.

The process turns uncertainty into explicit decisions. Each stage produces an output and a gate; implementation begins only after the documentation audit passes.

Phase A

Define the project

Establish the intended experience, boundaries and permanent system ownership before decomposing the build.

01IdeaCapture intent without pretending every detail is known.

Purpose and timing

Use at the beginning or when a project has lost its central reason to exist.

Inputs and questions

Start with the fantasy, audience, platform and constraints. Ask what the player repeatedly does, feels and understands.

Output and gate

A concise idea statement and a visible list of assumptions. Continue when the idea can be explained without relying on an unspoken feature list.

Common failure: solutioneering before the experience is clear. Example: “A tense observation game where attention is a limited resource.”

Related prompt foundation
02Project definitionConvert the idea into an agreed boundary.

Inputs and questions

Use the idea, constraints and experience review. Define goals, non-goals, success evidence, technical boundaries and unresolved decisions.

Output and gate

An approved project brief. Continue only when scope and non-scope are equally clear.

Common failure: writing aspirations that cannot be tested. Example: specify the supported platform and first playable boundary.

Project Brief foundation
03Module mapAssign permanent ownership.

Inputs and questions

Read the project definition and identify stable responsibilities, contracts and dependency direction—not screens or temporary tasks.

Output and gate

A module map with ownership and relationships. Continue when every core responsibility has one credible home and circular dependencies are challenged.

Common failure: treating folders or delivery slices as architecture.

See the structure model
Experience review

Challenge the experience before architecture hardens it.

  • What does the player repeatedly notice, decide and do?
  • Where does tension, relief or mastery come from?
  • What information must remain hidden or legible?
  • Which feature could be removed without breaking the promise?
  • What observable evidence would show the experience works?
Phase B

Prepare implementation

Resolve module contracts, define cross-module slices and translate them into auditable work.

04Module requirementsDefine responsibilities and contracts.

For each module, record purpose, owned state, inputs, outputs, events, constraints, dependencies, failure behaviour and test obligations.

Gate

Continue when the module can be implemented without inventing product behaviour. Missing decisions return to project definition.

Common failure: describing classes instead of required behaviour.

Module Requirements foundation
05Slice specificationsShape temporary, testable delivery units.

Combine approved module responsibilities into the smallest end-to-end behaviour that produces useful evidence. Record entry state, behaviour, affected modules, acceptance checks and exclusions.

Gate

Continue when the slice is independently demonstrable and does not redefine module ownership.

Common failure: slices that are technical layers with no observable result.

Modules and slices
06Task listsOrder bounded, verifiable actions.

Turn the slice into dependency-aware tasks. Every task names its scope, expected change, verification and stop condition.

Gate

Continue when the list can be executed in order and each completion claim can be checked.

Common failure: large tasks such as “build the system” with no evidence boundary.

Task List foundation
07Documentation auditProve the work is ready to build.

Audit consistency across the project brief, module map, requirements, slice specification and task list. Resolve contradictions rather than carrying them into code.

Gate

Implementation unlocks only when the audit passes or named exceptions are explicitly accepted.

Common failure: checking that documents exist instead of checking that they agree.

Documentation Audit foundation

Documentation audit checklist

  • Scope and non-goals remain consistent.
  • Every responsibility has a single module owner.
  • Inputs, outputs and dependency direction agree.
  • Each slice maps to approved requirements.
  • Tasks include verification and stop conditions.
  • Unknowns are resolved, deferred by name or treated as blockers.
  • No implementation detail silently changes the intended experience.
Phase C

Build and verify

Execute within the approved boundary, gather evidence and revise through controlled decisions.

08ImplementationBuild approved tasks with bounded context.

Load only the relevant project decisions, module requirements, slice and current task. Preserve unrelated work and stop when assumptions escape the approved boundary.

Gate

A task completes when the change exists, its specified checks pass and evidence is recorded.

Common failure: opportunistic refactors that widen the review surface.

Context strategy
09TestingCompare observable behaviour with intent.

Run the planned automated, integration and experience checks. Record what was tested, the result and any limitation.

Gate

Continue when acceptance evidence supports the slice and failures have a named owner.

Common failure: treating a successful build as proof of correct behaviour.

Test Plan foundation
10Controlled revisionChange deliberately without erasing approved intent.

Classify the discovery, identify affected documents and modules, assess risk, then approve or reject the revision before applying it.

Gate

Resume execution only when the new decision and its downstream effects are recorded.

Common failure: patching symptoms until documentation and implementation describe different projects.

Controlled Revision foundation

Execution controls

Classify work before deciding how much can happen together.
ClassMeaningDefault handling
IndependentNo shared state or ordering dependency.Safe to batch after scope checks.
SequentialOne result determines the next task.Complete and verify in order.
High-riskTouches architecture, persistence or broad behaviour.Isolate with tighter review.
DiscoveryTests an assumption rather than shipping a result.Time-box; report evidence, not completion.

Safe batching

Batch only independent tasks with separate targets, clear verification and no shared decision. Stop the batch when one result changes another task’s assumptions.

Resume protocol

  1. Read the latest approved resume card.
  2. Confirm phase, module, activity, status and next valid action.
  3. Load only the source documents needed for that action.
  4. Re-run the last meaningful check before changing code.
  5. Update the card before ending the session.

Conversation organisation

Keep definition, module planning, slice delivery and recovery discussions distinct. Carry approved decisions forward through source documents and resume cards instead of relying on chat memory.
