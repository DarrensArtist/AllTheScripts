Workflow · Structures

Give every decision, system and asset a credible home.

Structure is an ownership model first and a folder layout second. Permanent modules own behaviour; temporary slices organise delivery across those boundaries.

Modules and slices solve different problems.

Permanent ownership

Modules

Stable capability boundaries that own state, contracts and behaviour for the life of the project.

  • Named by responsibility
  • Define dependency direction
  • Survive multiple delivery phases
Temporary delivery

Slices

End-to-end increments assembled from one or more modules to produce testable evidence.

  • Named by outcome
  • Cross module boundaries deliberately
  • Close when accepted

Locked project tree

The top-level contract stays predictable. Folders beneath it are optional when a role has no content.

Assets/
├── _Project/
│   ├── Application/
│   ├── Modules/
│   ├── Shared/
│   ├── Scenes/
│   ├── Settings/
│   └── Tests/
└── ThirdParty/
Application

Composition, startup and project-wide orchestration. It connects modules but does not absorb their domain behaviour.

Modules

Permanent capability owners. Each module follows the role-based internal model below.

Shared

Deliberately cross-cutting utilities and primitives with no natural module owner. Keep this small.

Scenes

Scene assets and composition roots. The final convention for scene-root ownership remains under validation.

Settings

Project-level configuration that is not owned by a single module.

Tests

Cross-module and project-level tests; module-specific tests remain with the module.

ThirdParty

External packages kept visibly separate from project-owned work.

│   ├── Prefabs/
│   ├── UI/
│   ├── Animation/
│   ├── Audio/
│   └── VFX/
├── Editor/
└── Tests/

Folders are roles, not a quota. Create one only when content exists. Runtime owns executable domain behaviour; Configuration defines tunable data; Presentation owns visible or audible expression; Editor contains authoring support; Tests verify the module contract.

When placement is ambiguous

Ask ownership questions before creating another folder.

  • Which module would be incomplete without it?
  • Who controls its lifecycle and changes?
  • Is it truly reused unchanged, or only potentially reusable?
  • Does moving it to Shared hide a real dependency?

Conventions still under validation

Scene roots: scene composition belongs under Scenes, while domain behaviour stays in modules. The precise root/prefab convention will be confirmed through project use.

UI safe area: safe-area adaptation should be a reusable presentation concern with scene-level composition. Its final ownership boundary is intentionally not locked yet.
